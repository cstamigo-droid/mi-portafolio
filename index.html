Radar de Datos · Guardián PYME

Java · POO · interfaces · consola

Agente de consola que revisa un equipo y diagnostica riesgos de datos antes de que se pierdan: bases sin respaldo, datos personales expuestos, credenciales en texto plano y disco lleno. Seis detectores distintos detrás de una misma interfaz.

Sólo lee metadatos —nombres, tamaños, tipos— y nunca copia ni envía el contenido. Esa restricción se decidió antes de escribir el primer detector, porque una herramienta que revisa datos ajenos tiene que poder explicar qué no hace.

La prueba que importa es la del round-trip: empaquetar y descomprimir una carpeta y comprobar que los datos vuelven byte a byte. En una herramienta de respaldos, demostrar que se restaura es parte del producto. El checksum se valida además contra un SHA-256 calculado por fuera, como control positivo: sin eso, una implementación consistentemente equivocada pasaría igual.

02 Caso de estudio

De todo lo que construí durante el curso, esto es lo que mejor muestra cómo trabajo. No es el proyecto más grande: es el problema que más me costó, y el que más me enseñó.

Caso de estudio · SpringEduManager

El 401 que sí se generaba, y algo se comía tres pasos después

Agosto de 2026 · Java 21 · Spring Boot · Spring Security

La actividad
Cierre del proyecto del módulo de Spring: revisar la aplicación entera antes de presentarla, depurarla y dejarla lista para el portafolio. Gestiona estudiantes, cursos y evaluaciones, con dos roles y una API REST para integrarse con otros sistemas.
El desafío

La aplicación parecía terminada: compilaba, las pruebas pasaban y todos los flujos del navegador funcionaban. Al ejercitarla por HTTP encontré que la API respondía 302 —un redirect al formulario de login en HTML— cuando debía responder 401.

Para un navegador da igual. Para un programa que consuma la API es grave: sigue el redirect, recibe el HTML del login con estado 200, y no puede distinguir un rechazo de una respuesta válida. La promesa de interoperabilidad del proyecto no se sostenía.

Lo difícil no fue verlo: fue que el primer arreglo no funcionó. Declaré un punto de entrada explícito para la API y siguió devolviendo 302.

La solución

La causa real estaba un nivel más abajo, y sólo apareció al seguir la petición completa:

  1. Spring responde el 401 con sendError().
  2. Eso hace que Tomcat re-despache la petición internamente hacia /error.
  3. Ese re-despacho vuelve a pasar por el filtro de seguridad, pero ahora la ruta ya no calza con /api/**.
  4. La atiende la cadena web, que exigía autenticación, y sobrescribe el 401 con un 302.

El 401 sí se generaba; algo se lo comía después. La cabecera WWW-Authenticate sobrevivía porque ya estaba escrita, y esa contradicción fue la pista. El arreglo fue declarar /error como ruta pública: una línea. Encontrarlo fue el trabajo.

Herramientas

Java 21 · Spring Boot · Spring Security · Spring Data JPA · Maven · JUnit para el producto.

Para el diagnóstico, cURL sobre la aplicación corriendo, leyendo cabeceras y códigos de estado. Elegí esa herramienta a propósito: el problema era invisible desde el navegador y desde las pruebas unitarias, porque los dos ocultan el redirect. Sólo un cliente que no lo siga automáticamente lo muestra.

Las 35 comprobaciones quedaron en un guion reutilizable: la revisión dejó de ser un recorrido manual que hay que recordar y pasa a correrse en un comando. Las cifras de la tabla son las del día del arreglo; el guion siguió creciendo con el proyecto y al cierre del módulo corre 63 comprobaciones, con 42 pruebas automáticas al lado.

Aprendizajes
  1. Un código de estado correcto puede estar generado por el motivo equivocado. Cuatro de mis primeras comprobaciones fallaron y resultaron ser errores del guion de prueba, no del producto. La más peligrosa fue una que pasaba: devolvía 400 por un JSON mal formado, no por la validación. Estaba en verde sin medir nada.
  2. Probar desde el navegador no es probar una API. Son dos clientes distintos y sólo uno de los dos perdona.
  3. Cuando el primer arreglo no funciona, la hipótesis está mal. Insistir con variantes del mismo parche habría gastado horas; seguir la petición paso a paso lo resolvió.
Habilidades aplicadas
Depuración de una cadena de filtros de seguridad · configuración de Spring Security · diseño de respuestas de una API REST · manejo de excepciones con @RestControllerAdvice · pruebas de integración por HTTP · control de versiones con Git · documentación técnica del cambio.
Por qué elegí este caso

Porque muestra lo que quiero que se vea de mí, y no lo que quedó más lucido. Podría haber elegido el proyecto con más pantallas; elegí el problema donde todo indicaba que estaba terminado y no lo estaba.

Vengo de casi diez años en soporte de TI, arreglando lo que otros construían. De ahí me quedó la costumbre de no confiar en que algo funcione porque compila. Este caso es esa costumbre aplicada a mi propio código, y encontrar un error propio, admitir que el primer intento de arreglo falló y dejarlo documentado me parece mejor carta de presentación que un proyecto donde supuestamente nada falló.

03 Servicios y APIs

radar-mundo

Python · RSS · concurrencia · sin dependencias

Colector de acontecer mundial sin claves de API: reúne titulares de medios internacionales, los agrupa por historia y los ordena por cuántos medios distintos cubren lo mismo.

Lo que más me interesó resolver: un barrido a medias no puede parecerse a uno completo. Si tres de nueve fuentes no responden, el informe lo dice en la primera línea. Cero noticias porque no pasó nada y cero porque se cayó la red se ven igual en casi cualquier colector.

El criterio de corroboración lo corregí después de correrlo contra fuentes reales: la historia mejor rankeada decía «2 medios: BBC Business, BBC Tech» — un solo diario en dos secciones. Estaba inflando justo la señal que dice medir.

AEGIS

Python · FastAPI · PostgreSQL · Docker

Servicio que intercala una aprobación humana antes de que un proceso automático ejecute una acción sensible. Doce rutas documentadas y un control de duplicados para que reintentar una petición no la ejecute dos veces.

La idea salió de un problema concreto: si el cliente reintenta porque se cortó la red, el servidor no puede saber si es una acción nueva o la misma de antes. La respuesta fue que el cliente nombre cada operación.

06 Sistemas propios

Fuera del bootcamp mantengo software que otras personas usan todos los días. Vive en repositorios privados y por eso no lo enlazo, pero es donde aprendí lo que se ve arriba: que un sistema no está listo cuando compila, sino cuando sigue funcionando sin que nadie lo mire. Puedo mostrarlo en funcionamiento a quien lo pida.

Informe diario con usuario real
Servicio que cada mañana reúne datos de varias fuentes, aplica las reglas que definió el propio usuario y le envía un resumen por Telegram. Lleva meses corriendo solo, con una persona que no soy yo dependiendo de que llegue. Ahí aprendí que un error silencioso es peor que una caída: si no llega el mensaje, nadie se entera de que algo falló.
Gestión para una empresa que factura
Sistema en Java para la operación de una sociedad real: emisión y control de documentos tributarios, y vigilancia del plazo legal de ocho días para objetar una factura. Si ese plazo se pasa, la empresa pierde el derecho a reclamar; el sistema avisa antes. No es un caso de estudio: si falla, el costo es dinero.
Orquestación y tolerancia a fallos
Plataforma que coordina alrededor de noventa tareas programadas, con registro durable de eventos y panel de estado. Lo que más me enseñó: comprobar el efecto y no el código de salida. Una tarea puede terminar con éxito y no haber hecho su trabajo, y eso no se ve en los registros hasta que lo buscás a propósito.
